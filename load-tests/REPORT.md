# Итоговый отчёт: нагрузочное тестирование (эпик #51, НТ-1…НТ-9)

Дата прогонов: 29.09–01.10.2026. Стенд: учебный сервер предприятия
(`ediservdevelop`, Ubuntu 22.04, 4 ядра, 8 ГБ RAM), изолированные порты
`15433/18081/19090/13000`, backend в профиле `loadtest` (prod-like логи,
mock PrintSrv, heap `-Xmx512m`), генератор нагрузки k6 v2.3.0 на том же
хосте, мониторинг Prometheus + Grafana.

Все прогоны выполнены штатными командами `make load-*` (см.
[README стенда](README.md) и [runbook soak](SOAK_24H.md)) — методика
повторяема, на выделенном стенде команды те же.

## Детали

### Soak 24 часа (НТ-6, #68)

100 VU комбинированного сценария: 70 % подписчиков `/ws/live`,
20 % `/ws/unit`, 8 % REST-топология, 2 % login/refresh.

- **Память**: G1 Old Gen «пила» 65–90 МБ без монотонного роста; после
  схода нагрузки вернулся к 63–65 МБ. Утечки нет.
- **Сессии**: после остановки нагрузки `scada_ws_live_sessions` и
  `scada_ws_unit_sessions` вернулись в 0 — зависших сессий нет.
- **CPU**: плато 32 %, тренда роста за сутки нет (31,6–34,2 %).
- **Пул БД**: HikariCP стабильно 8 активных / 10 свободных соединений,
  0 таймаутов, очередь в ожидании соединения — 0.
- **Лог**: 0 ERROR за всё время.

Latency за сутки (клиент k6): топология p95 4,7 мс, refresh 11,9 мс,
login avg 175 мс / p95 288 мс / max 748 мс, WS snapshot p95 1 мс,
WS initial package p95 57 мс, WS units status p95 75 мс,
WS handshake p95 4 мс. Latency в конце окна равен latency в начале —
деградации за сутки нет.

### Spike «начало смены» (НТ-9, #71)

Мгновенный всплеск 0→500 VU за 10 секунд на `/ws/live`. Все 500 сессий
установлены (255 949 — за soak, здесь 2 219), ноль ошибок, серверная
метрика подтвердила peak ровно в 500 сессий. После схода — сессии в 0,
heap 134 → 91 МБ и ниже.

Характерная особенность: handshake p90 5,4 с / p95 6,7 с / max 8,4 с
(медиана 3,5 мс). Это не отказы, а очередь: за 10 секунд серверу
предъявляется 500 апгрейдов соединений, CPU уходит в пик 87 %, лишние
подключения ждут очереди. Важная оговорка: k6 работал на той же
4-ядерной машине и конкурировал за CPU с backend, реальная задержка на
выделенном продовом железе будет ниже. Сценарий разовый (все переподключаются
одновременно раз в смену), интерактивная работа после установки сессии
не страдает (snapshot p95 7 мс).

### Комбинированный стресс (НТ-4, #64)

Ступени 100 → 200 → 300 VU с пятиминутными паузами (combined.js).
300/300 достигнуто: 9 268 WS-сессий без единой ошибки, checks 100 %
(43 821/0), backend CPU ~57 %. Handshake med 2,7 мс / p95 6,2 мс —
плавный ramp не создаёт очередей (контраст со spike).

Потолок (breakpoint) намеренно не искали: сервер общий, рядом живут
другие проекты, дальнейший рост означал бы load average > 10 подольше.
Косвенный индикатор запаса — spike 500 WS без ошибок при CPU 87 %.

### Деградация PrintSrv (НТ-5, #66)

100 VU на `/ws/live` при трёх «мёртвых» инстансах PrintSrv
(`PRINTSRV_MOCK_OFFLINE_INSTANCES=bosch,grunwald11,grunwald1`, mock кидает
IOException на опросе). 2 042 сессии, 0 ошибок HTTP/WS, **0 ERROR в логе
backend** — недоступность части оборудования обрабатывается как штатная
ситуация, подписки и опрос остальных инстансов не ломаются.

## Выводы

Система **готова к выкатке на реальных пользователях** в рамках
проверенного диапазона: до 500 одновременных WebSocket-сессий на 4 ядрах
с запасом CPU ~40 %, без утечек памяти и зависших сессий при суточной
наработке, устойчива к отказу части оборудования.

### Сильные стороны (подтверждено прогонами)

1. **Стабильность на дистанции**: 24 часа, 680k HTTP + 256k WS-сессий,
   ноль ошибок, ноль утечек (soak).
2. **Чистая работа с сессиями**: после любого прогона сессии возвращаются
   в 0 — нет «зависших» соединений (soak, spike, НТ-4).
3. **REST дешёвый**: топология отдаётся за 4,7 мс p95 благодаря ETag/304.
4. **WS snapshot почти бесплатный**: p95 1 мс.
5. **Отказоустойчивость**: деградация PrintSrv не роняет backend (НТ-5).

### Слабые места и рекомендации (по убыванию важности)

1. **WARN-спам «Device composition mismatch»** — ~60 тыс. записей за сутки,
   98 % всего лога (soak). На стенде — расхождение mock PrintSrv с сидом
   топологии (benign), но на проде такой поток замаскирует реальные WARN
   и раздует лог. Рекомендация: привести mock к сиду и/или понизить уровень
   сообщения / задедуплицировать.
2. **Login — самый тяжёлый REST-эндпоинт** (BCrypt avg 175 мс, p95 288 мс,
   max 748 мс — soak). При массовом одновременном логине (начало смены)
   это первое узкое место. Рекомендация: оценить стоимость BCrypt-раундов
   под нагрузкой спайка логинов; при необходимости — снизить cost /
   ввести постепенную разогревающую выдачу токенов.
3. **Handshake-очередь при мгновенном всплеске** (НТ-9: p95 6,7 с при
   0→500 за 10 с). Рекомендация по инфраструктуре: ≥ 4 ядер на backend
   при ~500 сессиях; клиентам PWA разовая задержка подключения в первые
   минуты смены приемлема. Опционально — увеличить очередь accept'а
   Tomcat и смотреть повторно.
4. **Нет серверных latency-гистограмм** (`http_server_requests_seconds_bucket`
   не публикуется — percentile histograms выключены). Серверный p95 не
   считается без k6. Рекомендация: включить `management.metrics.distribution`
   для ключевых эндпоинтов в прод-профиле.
5. **Точка отказа (breakpoint) не найдена** — намеренно, из-за общего
   сервера. Рекомендация: повторить на выделенном стенде (этап 2 эпика),
   если понадобится число для capacity-планирования.
