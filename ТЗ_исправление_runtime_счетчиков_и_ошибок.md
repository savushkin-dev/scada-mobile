## 1. Цель

Исправить отображение счетчиков камер и ошибок устройств при работе с реальными runtime-данными PrintSrv/SCADA.

Старая SCADA должна считаться эталоном семантики полей. Необходимо сохранить единый результат в:

- общей карточке автомата;
- деталях автомата, вкладка «Устройства»;
- деталях автомата, вкладка «Журнал»;
- live-алерте и красном статусе карточки автомата.

Mock-снимки, mock-симулятор и mock-конфигурация в рамках этого ТЗ не изменяются и не используются как источник требований.

## 2. Область изменений

Изменения должны затронуть только runtime-путь:

```text
реальный PrintSrv -> polling -> snapshot -> маппинг runtime-полей -> UnitErrorStore/DTO -> WebSocket -> frontend
```

Основные точки реализации:

- `backend/src/main/java/dev/savushkin/scada/mobile/backend/services/UnitDetailService.java`;
- `backend/src/main/java/dev/savushkin/scada/mobile/backend/services/WorkshopService.java`;
- `backend/src/main/java/dev/savushkin/scada/mobile/backend/services/ScadaKeyMapper.java`;
- при необходимости отдельный backend-мэппер runtime-тегов;
- связанные DTO и frontend-компоненты только если текущий контракт не позволяет отобразить исправленные данные.

## 3. Runtime-источник данных

Backend должен читать фактические `Key -> Value` из runtime-ответа PrintSrv, а не названия объектов/свойств, отображаемые в редакторе старой SCADA.

Нужно поддержать различие между:

- экранным объектом старой SCADA, например `CMSDev041`;
- фактическим runtime-префиксом, например `Dev041`;
- фактическим ключом свойства, например `Dev041Fail` или `Dev041CounterMissing`.

Перед реализацией необходимо на одном реальном ответе PrintSrv для Grunwald 5 подтвердить точные имена ключей. Логика не должна зависеть только от визуальной подписи `CMSDev041` или `Connect`.

Если в runtime встречаются разные варианты написания одного и того же поля, они должны нормализоваться в backend в одну внутреннюю модель.

## 4. Проблема 1: счетчики камер

### 4.1. Канонические поля

Для каждой камеры агрегации, камеры агрегации на коробе и EAN-камеры приоритетными являются SCADA-поля:

| Поле UI | Основной runtime-тег | Семантика |
|---|---|---|
| «Считано» | `DevXXXCounterGeneral` | общее количество обработанных/считанных кодов |
| «Несчитано» | `DevXXXCounterMissing` | количество непрочитанных/отсутствующих кодов |

Для примера из старой SCADA:

- первая aggregation-камера: `Dev041CounterGeneral`, `Dev041CounterMissing`;
- первая aggregation-box-камера: `Dev042CounterGeneral`, `Dev042CounterMissing`.

Префикс `XXX` нельзя выбирать по жестко заданному имени камеры. Он должен определяться тем же подтвержденным маппингом, который используется старой SCADA и runtime-конфигурацией конкретного автомата.

### 4.2. Fallback-счетчики

Если основной тег отсутствует, пустой или не может быть прочитан, использовать fallback в следующем порядке:

1. прямое поле камеры `Total` для «Считано»;
2. прямое поле камеры `Failed` для «Несчитано».

Fallback применяется отдельно к каждому полю. Например, наличие `CounterGeneral` не должно запрещать fallback только для отсутствующего `CounterMissing`.

Нулевое значение `0` является валидным значением и не должно заменяться fallback-тегом.

Пустое значение, отсутствие ключа и ошибка чтения считаются отсутствием значения.

### 4.3. Единый результат

Один и тот же resolved-результат счетчиков должен использоваться:

- в `DEVICES_STATUS` для карточки каждой камеры;
- в `LINE_STATUS`/`UNITS_STATUS` для счетчиков на общей карточке автомата.

Нельзя оставлять разные правила: общая карточка не должна читать только `Total/Failed`, если вкладка деталей уже использует `CounterGeneral/CounterMissing`.

Если на автомате несколько камер, алгоритм выбора общей пары должен быть явно сохранен, но выбранная камера должна разрешать счетчики через приоритетные SCADA-теги. Предпочтительный порядок групп:

1. `aggregationCams`;
2. `aggregationBoxCams`;
3. `checkerCams`, если для них подтверждены счетчики.

Не суммировать счетчики разных камер без подтвержденной семантики: счетчики могут описывать один и тот же поток и тогда двойной подсчет будет ошибкой.

## 5. Проблема 2: ошибки устройств

### 5.1. Ошибочные поля из старой SCADA

Для объектов камеры, отображаемых в старой SCADA как `CMSDev041`, `CMSDev042` и т. п., должны обрабатываться следующие флаги:

| Поле старой SCADA | Канонический суффикс backend | Смысл |
|---|---|---|
| `Connect` или `Connection` | `Connection` | нет связи с устройством |
| `Fail` | `Fail` | нет кодов маркировки/ошибка проверки |
| `DiffEan` | `DiffEan` | несовпадение EAN |
| `Dublicate` | `Dublicate` | одинаковые коды |
| `Work` | `Work` | нет данных с устройства |
| `Data` | `Data` | нет данных, дополнительный флаг |
| `Batch` | `Batch` | несовпадение партии |
| общий `Error` | `Error` | общая ошибка устройства |

Приоритет должен быть у фактического runtime-тега, соответствующего полю старой SCADA. Например, при подтвержденном формате:

```text
Dev041Fail
Dev041DiffEan
Dev041Dublicate
Dev041Work
```

эти ключи должны обрабатываться непосредственно.

### 5.2. Fallback для имен тегов

Нужно поддержать fallback-распознавание только для подтвержденных runtime-вариантов:

- префикс `DevXXX`;
- префикс `CMSDevXXX`, если он реально присутствует в ответе PrintSrv;
- суффикс `Connection` и его runtime-вариант `Connect`;
- варианты, относящиеся к принтерам: `LineDevNNN...` и фактические runtime-ключи принтера.

Fallback не должен превращаться в поиск по подстроке. Ключ должен разбираться на известный префикс устройства и полный известный суффикс ошибки, чтобы не создавать ложные ошибки.

Необходимо сохранить оригинальный runtime-ключ в поле `propertyDesc`, чтобы по журналу можно было сравнить данные проекта с ключом старой SCADA.

### 5.3. Активность ошибки

Флаг считается активным, если его значение:

- существует;
- не пустое;
- после удаления пробелов не равно `0`.

Значения `1`, `true` и другие подтвержденные runtime-значения активности должны поддерживаться без изменения семантики текущего PrintSrv-контракта. Нельзя считать активным произвольное нечисловое значение без явного правила.

### 5.4. Ошибка должна влиять на все нужные представления

Если активен любой подтвержденный флаг `Fail`, `DiffEan`, `Dublicate`, `Work`, `Data`, `Batch`, `Connection` или `Error`, то:

- ошибка должна попасть в `UnitErrorStore`;
- для автомата должен формироваться `ALERT`;
- общая карточка автомата должна стать критической;
- ошибка должна попасть во вкладку «Журнал»;
- ошибка должна быть привязана к правильному устройству (`Dev041`, `Dev042`, `LineDev011` или нормализованное имя устройства).

Наличие только общего `Error` не должно быть обязательным условием для формирования алерта. В частности, `Fail=1` или `DiffEan=1` уже являются активной ошибкой, если так трактует старая SCADA.

## 6. Состав и маппинг устройств

### 6.1. Источник состава

Для runtime необходимо сопоставить:

- устройства, реально перечисленные PrintSrv в `LineDevices`/аналогичном runtime-поле;
- устройства, зарегистрированные в topology БД;
- объекты `DevXXX` в snapshot `scada`.

Ошибка `Dev041` или `Dev042` не должна молча отбрасываться только потому, что камера отсутствует в устаревшей записи БД, если runtime однозначно сообщает о наличии этой камеры.

Нужно выбрать и зафиксировать один из вариантов:

1. runtime-состав является основным, БД используется fallback;
2. БД остается основным источником, но runtime-устройства автоматически получают корректный активный тип и участвуют в обработке ошибок;
3. для обработки ошибок используется отдельный runtime-маппинг, независимый от отображаемой topology.

Предпочтителен вариант, который не теряет реальную ошибку при рассинхронизации БД и PrintSrv.

### 6.2. Индексный маппинг

Текущий индексный маппинг допустим только если подтвержден реальными данными:

```text
aggregationCams[0]       -> Dev041
aggregationBoxCams[0]    -> Dev042
aggregationCams[1]       -> Dev043
aggregationBoxCams[1]    -> Dev044
```

Для Grunwald 5 необходимо отдельно подтвердить, что `Dev041` и `Dev042` действительно соответствуют показанным на скриншоте объектам камер, а не только совпадают по позиции в массиве.

Если реальный PrintSrv предоставляет прямое имя связи камеры с `DevXXX`, использовать прямое соответствие вместо незащищенного индексного предположения.

## 7. Требования к backend

1. Создать или расширить единый runtime-мэппер тегов, чтобы логика счетчиков и ошибок не дублировалась в `UnitDetailService` и `WorkshopService`.
2. Реализовать разрешение счетчиков с приоритетом `CounterGeneral/CounterMissing` и независимым fallback на `Total/Failed`.
3. Реализовать разбор и нормализацию всех подтвержденных error-флагов старой SCADA.
4. Не фильтровать активную ошибку только по наличию камеры в устаревшей БД-топологии.
5. Сохранить оригинальный ключ и понятное описание ошибки.
6. Добавить диагностическое логирование при обнаружении активного runtime-флага:
   - instance id;
   - исходный runtime-ключ;
   - значение;
   - нормализованное устройство;
   - выбранный источник счетчика, если речь о счетчиках.
7. Не логировать каждый нулевой флаг на уровне `WARN` или `INFO`.
8. При неизвестном префиксе/суффиксе не создавать ложную ошибку, но выдавать диагностическое сообщение, позволяющее добавить новый runtime-вариант.
9. Обновить backend-тесты для реальных форматов ключей и fallback-сценариев.

## 8. Требования к frontend

1. Не менять названия пользовательских полей: «Считано», «Несчитано», «Ошибка».
2. Не вычислять ошибки камер самостоятельно во frontend. Frontend отображает backend-модель.
3. Не подменять отсутствие счетчика нулем там, где backend сообщил отсутствие данных. Если обратная совместимость требует отображения `0`, это должно быть явно документировано.
4. Красный статус устройства не должен зависеть только от поля `Error`, если backend уже передал активный профильный error-флаг.
5. Общая карточка автомата должна использовать `ALERT`, сформированный из того же источника ошибок, что и вкладка «Журнал».
6. Сохранить текущий WebSocket-контракт, если для исправления достаточно backend-нормализации.

## 9. Проверка runtime

Проверка выполняется только на реальном PrintSrv, в первую очередь на Grunwald 5.

### 9.1. Снять исходные данные

В момент, когда старая SCADA показывает ошибку, получить raw-ответы:

- snapshot `scada`;
- snapshot `Line`;
- snapshot каждой камеры, связанной с автоматом;
- актуальный состав устройств.

Нужно сохранить пары `Key -> Value`, а не только скриншот подписей.

### 9.2. Проверить счетчики

Для первой и второй камеры проверить наличие и значения:

```text
Dev041CounterGeneral
Dev041CounterMissing
Dev042CounterGeneral
Dev042CounterMissing
```

Также проверить fallback:

```text
Total
Failed
```

Проверить отдельно сценарии:

- основной тег присутствует и равен `0`;
- основной тег отсутствует;
- основной тег пустой;
- присутствует только один из двух основных тегов.

### 9.3. Проверить ошибки

Для каждого активного объекта из старой SCADA сопоставить:

```text
CMSDev041 / Dev041
CMSDev042 / Dev042
Connection / Connect
Fail
DiffEan
Dublicate
Work
Data
Batch
Error
```

Зафиксировать:

- точное имя runtime-ключа;
- значение в момент ошибки;
- ожидаемый объект в приложении;
- наличие ошибки в `ALERT`;
- наличие ошибки в `ERRORS`;
- цвет общей карточки автомата;
- цвет карточки конкретного устройства.

### 9.4. Контрольные точки backend

Для одного polling-цикла проверить последовательно:

1. raw snapshot `scada` содержит активный ключ;
2. `extractActiveErrors(instanceId)` возвращает соответствующий `DeviceError`;
3. `UnitErrorStore` содержит ошибку;
4. `AlertService.computeAlertForInstance(instanceId)` возвращает активный alert;
5. `ALERT` содержит правильный `unitId` и устройство;
6. `ERRORS` содержит ту же ошибку.

Если ошибка исчезла на шаге 2, frontend и WebSocket не являются причиной.

## 10. Критерии приемки

Задача считается выполненной, если на реальном Grunwald 5:

1. Значения «Считано» и «Несчитано» совпадают со старой SCADA при наличии `CounterGeneral/CounterMissing`.
2. При отсутствии основных счетчиков корректно работает fallback `Total/Failed`.
3. Валидный нулевой `CounterMissing` не заменяется значением `Failed`.
4. Любой активный подтвержденный флаг ошибки из набора SCADA отображается как ошибка автомата.
5. Ошибка `Dev041`/`Dev042` не теряется из-за отсутствия или устаревания записи камеры в БД, если runtime-связь подтверждена.
6. Одна и та же ошибка присутствует в общей карточке, `ALERT` и журнале деталей.
7. Ошибка устройства не зависит только от общего поля `Error`.
8. После снятия флага старая ошибка исчезает из `UnitErrorStore`, `ALERT` получает событие разрешения, карточка возвращается в нормальный статус.
9. Для неизвестного runtime-ключа нет ложного алерта, но есть диагностическая запись.
10. Добавлены backend-тесты минимум для:
    - приоритета `CounterGeneral/CounterMissing`;
    - fallback `Total/Failed`;
    - активных `Fail`, `DiffEan`, `Dublicate`, `Work`, `Connection`;
    - маппинга `Dev041` и `Dev042`;
    - отсутствия камеры в БД при наличии подтвержденного runtime-состава.

## 11. Ограничения

- Не изменять mock XML, mock simulator и mock registry.
- Не добавлять frontend-логику, дублирующую backend-правила.
- Не суммировать счетчики разных камер без подтверждения их независимости.
- Не считать `ST` самостоятельной ошибкой: `ST` описывает состояние работы устройства, а error-флаги определяются отдельными свойствами.
- Не переименовывать историческое написание `Dublicate` в runtime-ключах.
- Не подменять экранные имена старой SCADA фактическими runtime-ключами без проверки raw-ответа PrintSrv.
- Не ломать существующий WebSocket API без необходимости.
